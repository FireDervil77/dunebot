# Umbau der Sperrkette — die Schritte, die Root brauchen

Gehört zu `docs/Sperrsystem.md`. Entscheidungen des Betreibers vom 2026-09-16.

**Alles in der Anwendung ist bereits gebaut und committet.** Hier steht nur,
was Claude nicht selbst tun kann, weil es `/etc/fail2ban/` anfasst.

> Reihenfolge einhalten. Nach jedem Schritt steht eine Probe. Es gibt zu keinem
> Zeitpunkt ein Loch: Der Exploit-Blocker in der Anwendung läuft durchgehend.

---

## Schritt 1 — Fristen überall statt „für immer"

**Entscheidung:** *„Ja wir geben überall eine Frist. Auch wenn es dann die
Idioten dazu bringt, wieder zu kommen."*

Heute steht `bantime = -1` als Grundwert in `jail.local` und zusätzlich in
`[sshd]`, `[apache-badbots]`, `[apache-noscript]`, `[apache-overflows]`. Die
eigene DDoS-Datei warnt davor: eine dynamische DSL-Adresse trifft nach der
Zwangstrennung den Nächsten.

**Gegen das Wiederkommen hilft nicht „für immer", sondern Steigerung.**
fail2ban 0.11 kann das von sich aus: Jede Wiederholung verdoppelt die Frist,
bis zu einer Obergrenze.

```bash
sudo cp /etc/fail2ban/jail.local /etc/fail2ban/jail.local.bak-20260916
sudo nano /etc/fail2ban/jail.local
```

Im **ersten** `[DEFAULT]`-Block `bantime = -1` ersetzen durch:

```ini
bantime  = 86400              # 24 Stunden
bantime.increment = true      # jede Wiederholung verlängert
bantime.factor    = 2         # 1 d → 2 d → 4 d …
bantime.maxtime   = 1209600   # Obergrenze: 14 Tage
```

Dann in `[sshd]`, `[apache-badbots]`, `[apache-noscript]` und
`[apache-overflows]` die Zeile `bantime = -1` **löschen** — sie erben dann den
Grundwert samt Steigerung.

> **Nebenbei:** `jail.local` hat **zwei** `[DEFAULT]`-Blöcke (Zeile 1 und 74).
> Der zweite setzt nur `dbfile`/`dbpurgeage`. Das ist gültig, aber verwirrend —
> die zwei Zeilen gehören in den ersten Block, der zweite kann weg.

```bash
sudo fail2ban-client --test          # Konfiguration prüfen, BEVOR neu geladen wird
sudo systemctl reload fail2ban
sudo fail2ban-client get sshd bantime # muss 86400 sagen, nicht -1
```

## Schritt 2 — Die Exploit-Regel stilllegen

**Entscheidung:** *„ja wenn die exploit regel Sinn macht."* — Sie macht keinen
mehr. Begründung in `security/AUSSER-BETRIEB.md`.

```bash
sudo rm /etc/fail2ban/jail.d/dunebot.local
sudo rm /etc/fail2ban/filter.d/dunebot-exploits.conf
sudo systemctl reload fail2ban
sudo fail2ban-client status          # dunebot-exploits darf nicht mehr auftauchen
```

---

## Schritt 3 — Die Website-DDoS-Regel abschalten

**Entscheidung:** *„DDoS bezieht sich ja meist auf bestimmte Dienste, die wir eh
nicht anbieten … und ignorieren den Rest für die Website, damit wir nix mehr
aussperren."*

**Warum das richtig ist:** `dunebot-ddos` ist kein DDoS-Schutz. Gegen echten
volumetrischen Beschuss hilft fail2ban ohnehin nicht — die Pakete sind da, bevor
iptables sie verwirft; das muss der Anbieter oder ein vorgelagerter Dienst
abfangen. Was die Regel tatsächlich tut, ist **Scanner-Erkennung über
Fehlerantworten** — und das tut der Exploit-Blocker in der Anwendung schon,
genauer und sichtbar.

```bash
sudo cp /etc/fail2ban/jail.d/dunebot-ddos.conf /etc/fail2ban/jail.d/dunebot-ddos.conf.bak-20260916
sudo sed -i 's/^enabled  = true/enabled  = false/' /etc/fail2ban/jail.d/dunebot-ddos.conf
sudo systemctl reload fail2ban
sudo fail2ban-client status          # dunebot-ddos darf nicht mehr auftauchen
```

**Der Schwellwert, den man sehen kann**, wandert damit aus dem Daemon in ein
Werkzeug, das nichts kaputt macht:

```bash
sudo bash scripts/messen-fehlerrate.sh
```

Es zeigt je Adresse die stärkste Minute und die Pfade — dieselbe Bedingung, die
die Regel gezählt hat, nur ohne Sperre. Wenn dort eines Tages jemand mit 3000
Fehlern je Minute steht, kann die Regel jederzeit zurück (`enabled = true`).

## Was danach die Website schützt

| Ebene | Wer | Folge |
|---|---|---|
| Menge | `generalLimiter` / `apiLimiter` / `authLimiter` | **429**, nie eine Sperre |
| Absicht | Exploit-Blocker in der Anwendung | **403**, Eintrag in `blocked_ips` |
| bekannt | `blocked_ips` | **403**, seit 2026-09-16 alle 5 Minuten neu gelesen |

**fail2ban sperrt danach niemanden mehr wegen der Website.** Es bleibt für SSH
und die anderen Anwendungen zuständig — also dort, wo wir wirklich angreifbar
sind. Genau so war die Entscheidung.
